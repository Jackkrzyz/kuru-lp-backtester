## Findings to correct

### 1. High: job status can stop the UI before the worker stops

Sources: `kuru_backtester/server/backtest_jobs.py:223`,
`kuru_backtester/server/backtest_worker.py:67`, and `frontend/app.js:412`.

After 120 seconds without a progress callback, the manager writes terminal
`stalled` status even if the process is alive. The UI then stops polling.
Historical loading, grid generation, and output writing do not have an
independent heartbeat. A slow step can thus hide a result that later completes.

Isolated result: an alive mock worker with old progress returned `stalled`.
This confirms the state transition, not that a current user job has stalled.

Proposed fix: separate process heartbeat from event progress. Treat delayed
progress as a warning while the worker is alive. If a hard limit is reached,
stop the owned worker before publishing a terminal failure. Test a slow load,
slow write, real worker exit, cancellation, and late completion.

### 2. Medium: an abandoned queued job has no recovery path

Source: `kuru_backtester/server/backtest_jobs.py:206`.

After an abrupt server exit between writing queued status and starting a
worker, the new manager has no process handle. Status only applies its timeout
to `running`, not `queued`. The old record can stay queued without limit.

Isolated result: an old queued record with no worker returned `queued`.

Proposed fix: reconcile nonterminal records at startup. Use an ownership lease
and worker identity, not an unchecked PID. Mark abandoned work as interrupted.
Do not kill or adopt an unrelated process. Test restart at each launch stage.

### 3. High before public hosting: local access rules are not proxy-safe

Source: `kuru_backtester/server/backtest_server.py:66` and `:239`.

The origin check requires `http://Host`. A valid HTTPS browser origin is
rejected. Conversely, a loopback-bound server has no access token. A public
proxy that forwards requests without an Origin header can reach that server.
The same access gate protects backtests and download controls; there are no
separate public-user and data-admin roles.

Isolated results: same-host HTTPS origin returned `False`; a request without
Origin to a token-free handler returned `True`.

Do not expose this local server through a public tunnel unchanged. Add an
explicit public origin, trusted-proxy policy, secure sessions, and separate
admin authorization. Keep data downloads private. Test HTTPS requests,
cross-site requests, forged forwarding headers, and unauthorized admin calls.

### 4. Medium: the grid-size limit is checked after the expensive work

Sources: `kuru_backtester/server/backtest_service.py:924`,
`sdk_reference/browser_adapter.js:91`, and `frontend/app.js:286`.

The backend checks its 20,000-order limit after the SDK has generated the grid.
The browser also runs the SDK on its main thread. Revision checks reject stale
answers but do not stop the work that produced them. Wide ranges and small fee
steps can consume time before the limit is applied.

This is a source-based risk; no large stress case was run during the download.
Add a safe preflight bound consistent with the SDK. Keep exact grid validation
after generation. Move browser generation to a Web Worker and apply bounded
work and cancellation. Do not truncate or change the generated position.

### 5. Medium: the internal SDK HTTP server still has an unguarded write

Source: `kuru_backtester/server/sdk_grid_broker.py:163`.

The public response helper handles closed connections, but the local SDK
broker writes directly to `wfile`. If a job is canceled or its client times
out during generation, that write can still raise a broken-pipe error.
This is a remaining possible path, not proof of the user's earlier traceback.

Use the same narrow disconnect handling at this boundary. Do not hide SDK
generation errors. Test a client that closes while generation is in progress.

### 6. Low: recovery messages still name removed controls and launchers

Source: `kuru_backtester/server/backtest_service.py:486`, `:517`, and `:954`.

Some errors suggest old root Python commands or the removed Auto-fill button.
Replace these with the current command menu and manual deposit instructions.
Add tests so each suggested command exists. No message was changed in this review.

## Speed work, in order

1. Add timings for cold load, checkpoint replay, grid generation, simulation,
   compact output, and response transfer. Keep status latency separate from
   engine throughput. Use a bounded benchmark when no download is active.
2. Add a hash-bound block-offset and timestamp/count sidecar for immutable
   event partitions. `HistoricalEventStore.timestamps()` parses JSONL, and
   `iter_events()` reads it again. Arbitrary starts also scan earlier lines.
   A verified offset index can skip those reads without changing event order.
3. Cache verified start states with a strict memory bound and content identity.
   `BacktestService.load_range()` reconstructs the start before the result-cache
   check. Each child creates a new service. Repeated requests still do setup
   work, even when a complete matching result exists. Never share mutable books.
4. Make the preview worker cancel stale requests. Measure SDK time before
   changing rendering. Preserve the same order-grid bytes and raw integers.
5. Add safe expiry for completed job copies and results. Protect active jobs,
   checkpoints, and historical archives. Report retained bytes. Do not delete
   any current user artifact as part of this review.

Require identical golden summaries, fills, and deterministic hashes after each
speed change. Do not use floating-point arithmetic, GPU batching, or a language
rewrite as a shortcut around exact event order. No new speedup is claimed here.
